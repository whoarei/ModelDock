ModelDock 技术方案

以节点为执行边界，以插件为部署和环境维护单元。统一 Python 接入协议，将本机和 SSH 执行封装在同一任务模型下。

本文同时标明整体设计和 0.1.0 的实现选择。Rust 提供桌面系统能力和受控进程桥，本机与远端共享 Python 控制器。插件字段与 API 以独立的 Python 插件协议 为准，产品范围见 产品方案。
01

设计约束与技术决策

决策采用方案原因与边界
桌面外壳Tauri 2 + Rust；React + TypeScript + Vite。前端负责交互与可视化，Rust 负责系统能力、调度和数据管理。
模型接入版本化 Python SDK + 插件清单。模型代码复用 Python 生态；新增已有任务类型的模型无需修改 Rust 调度代码。
环境归属每节点、每插件一个启用环境，由 uv 准备。环境属于插件节点安装；运行方案切换和升级可短暂保留候选/回滚目录。
推理进程每个执行任务启动插件工作进程，批量任务内复用已加载模型。隔离任务崩溃、支持强制停止；环境不随任务重复创建。
远程访问SSH 控制与事件通道，SFTP 分发文件。复用 SSH 认证与加密；远端运行器不需要对外开放业务端口。
持久化本机 SQLite + 文件产物；远端控制器用标准库 SQLite 保存任务。状态可恢复，连接断开后按任务编号查询；大文件不写入数据库。
首批运行后端ONNX Runtime CPU；GPU 通过已验证的插件运行方案提供。不在统一环境中混装互斥运行包，避免硬件后端选择隐含在全局环境里。

首个完整版本按 M0/M1/M2/M3 分阶段交付，包括 Windows 本机执行和 SSH Linux 执行。首版每节点最多运行一个测试任务，避免平台内任务争用资源影响测试；外部进程负载仍需记录。

ModelInstanceid、name、plugin_id、model_id、weights_digest、labels_digest、config_snapshot。逻辑实例不依赖某一个物理路径；修改形成新的配置修订。

05

插件包与运行方案的系统集成

插件包由清单、Python 代码、支持模型配置与参数描述，以及运行方案依赖项目组成。模型权重独立管理；插件列表与模型实例分开建模。

字段与目录的完整约定移至 插件目录与交付包、插件清单 和 支持模型与参数描述。本文保留部署和生命周期职责，不重复维护字段定义。

平台负责安全解包、摘要校验、兼容性检查、节点安装和启用。一个节点安装只启用一个运行方案；CPU/GPU 方案分别锁定依赖，切换方案时按下文的 uv 生命周期准备候选环境。

YOLO 输出约定、SDK 依赖与结果模式必须在插件层声明并验证。新增已有任务类型的模型通过插件扩展；新任务类型需要扩展协议与前端视图。

06

Python 插件协议的系统边界

插件作者使用统一 load / predict / close 接口，本机和 SSH 节点不改变 Python API。SDK/Worker 负责类型与结果校验、上下文、计时辅助、日志和取消；插件只负责模型能力。

独立的 Python 插件协议 是清单、接口与结果格式的定义来源，重点包括：

  • 调用生命周期、上下文与输入。
  • 分类结果、检测结果及可视化产物。
  • 计时扩展、错误和取消、版本兼容。

前端按标准任务协议渲染，不直接解析模型张量。分段统计只来自 SDK 的测量能力；未提供可靠分段时显示不支持。任务统计、传输耗时和资源采样由系统负责。

07

uv 环境准备与生命周期

uv 作为随应用分发并固定版本的工具。插件安装、更新或修复时创建环境；测试运行直接启动已准备环境中的 Python，不执行隐式依赖解析或更新。

阶段行为结果
兼容检查检查平台、方案、SDK、Python 要求与可写目录。不兼容时停止准备并返回明确原因。
解释器准备使用 uv 管理的指定 Python 版本，记录实际完整版本与可执行文件。不依赖用户全局 Python，不改系统默认版本。
环境同步指定候选环境目录，按 uv.lock 执行锁定同步。保留依赖日志与环境指纹。
健康检查导入 SDK/入口、检查后端和设备，必要时执行样例加载。区分插件环境可用与某个模型实例可用。
启用节点内加插件操作锁，任务排空后切换 current 指针。检查失败保留旧环境；成功后按策略清理旧目录。
修复/卸载按指纹重建，或在无活动任务时删除该节点插件安装。不删除独立模型权重和历史结果。
# 概念命令：由应用传递参数与环境变量，不让用户手动执行。
# UV_PROJECT_ENVIRONMENT 指向当前候选环境的绝对路径。
uv sync --project <plugin>/runtime/cpu --locked --no-dev

# 运行阶段直接启动已准备解释器：
<environment-python> -m modeldock_worker --task-file <task.json>

环境指纹涵盖插件包摘要、方案、依赖项目与锁文件摘要、实际 Python 版本、平台/架构、SDK 和 uv 版本。驱动与硬件信息作为节点检查记录保存，变化后重新验证。

依赖项目设置为不需要安装项目本身的运行依赖集合；插件代码目录由 Worker 作为明确的代码根加载。SDK wheel 等本地依赖在插件包中保持固定相对位置。

uv 的缓存可减少下载与部分安装开销；环境仍可能占用独立空间。远端在自己的系统上创建环境，锁文件需涵盖目标平台，原生依赖和 GPU 驱动逐项验收。

在线准备失败可重试；离线准备要求可用的 uv、Python 安装介质、完整依赖包/缓存和权重。仅有锁文件不满足离线安装条件。已就绪环境的正常本机测试不联网。

目录布局与文件归属

本机可变数据放在用户数据目录，例如 %LOCALAPPDATA%/ModelDock；安装目录只存程序和工具。远端默认使用 $XDG_DATA_HOME/modeldock，未设置时使用 ~/.local/share/modeldock，也可选其他可写目录。

<data-root>/
  app.sqlite                      # 本机配置；远端用 tasks.sqlite
  tools/                          # uv、Python 与版本化控制器
  plugins/<plugin-id>/
    current.json                  # 启用的版本、方案和环境指纹
    releases/<version>-<digest>/   # 不可变插件内容
    envs/<fingerprint>/            # 插件环境；只有一个启用
    staging/                      # 更新候选，完成后清理
  artifacts/sha256/<digest>/       # 导入/上传的权重、标签和输入缓存
  jobs/<task-id>/
    task.json                     # 不可变配置与输入清单
    results.jsonl
    metrics.json
    logs/
    outputs/

外部已有权重和数据目录以显式节点路径引用，不强制复制进内容缓存。提交任务时记录文件大小、修改时间及内容摘要；使用前后验证变化，变化则使复现检查失败。缓存文件按摘要验证，禁止悄悄替换运行中的权重。

上传先写临时文件，校验大小及 SHA-256 后原子重命名。首版支持完整文件重试和命中缓存时跳过传输；分块续传可后续实现。删除缓存先检查引用和活动任务，原始外部文件不纳入自动清理。

执行器接口与通信协议

应用使用统一命令接口，经 Rust 桥调用 Python 控制器；控制器依据 node_id 选择本机或 SSH 转发。以下为 0.1.0 命令映射。

能力0.1.0 实现与边界
state / probe节点能力、插件与安装状态、模型实例、最近任务。
import_plugin / install_plugin / uninstall_plugin包登记、异步环境准备、环境卸载。
create_model权重/类别导入并执行 load/close 检查。
start_task / retry_task幂等任务登记；按已记录配置创建新的重测任务。
task_detail / cancel_task状态、样本结果、日志和报告；执行端确认取消。
preview / export按需获取原图/产物预览及 JSON/CSV 报告。

控制消息为 UTF-8 JSON。插件 stdout/stderr 作为日志，不由插件手写应用协议。任务状态更新和内部事件记录在 SQLite 中提交，首版界面定期查询；连续 JSON Lines 事件订阅属于后续接口。

相同 task_id 与相同配置重复提交返回原任务，不同配置返回冲突。网络超时后先查询原 task_id。原始权重和图片通过文件传输，预览使用有界图像数据；任务所在节点与路径来源明确分开。

10

SSH 部署、后台执行与重连

连接与部署

  1. Rust 建立 SSH 会话并验证 known_hosts/主机指纹；首次连接由用户核对，指纹变化时阻止静默信任。
  2. 通过 SFTP 创建可写工作目录，上传固定版本工具、节点控制器和插件构件，校验摘要。
  3. 在节点本地用 uv 准备插件环境。依赖从远端可访问的源下载，必要时走明确配置的镜像或离线包。
  4. 运行能力检查，包括后台任务在 SSH 断开后的存活测试。失败时显示不受支持的能力及原因。

任务执行

SSH 命令入口是固定、受控的控制器启动命令。结构化任务参数经标准输入或任务文件传入；路径使用 SFTP 操作，避免把用户字段直接拼接进远程 shell。

远端控制器将任务事务性登记到 SQLite，由节点监督进程调度。监督进程脱离当前 SSH 会话，标准输入输出重定向到受控文件；Worker 再使用插件环境启动。没有面向公网的任务服务端口。

可使用节点可用的用户级服务管理器维持监督进程；直接脱离会话的方式必须通过该节点的存活检查。某些主机会清理登出用户进程，不能仅凭使用 nohup 就声称支持断线续跑。

恢复与取消

SSH 通道断开只改变可达状态。重连后查询任务快照，按最后事件序号补齐。远端终态覆盖本机缓存。取消在执行端登记，先协作停止，超时后终止该任务工作进程组，再写入终态。

主机重启或进程异常后，控制器核对进程身份与任务登记；确认工作进程不存在则标记失败及中断原因。首版恢复查询与结果，不自动恢复已经中断的模型计算。

认证首版优先支持密钥和可用的 SSH agent。凭据放入系统凭据库，数据库仅存引用。具体 Rust SSH/SFTP 库需在 M0 验证 Windows 打包、密钥算法、agent 和流式事件能力后确定。

任务调度与状态一致性

CREATED → QUEUED → PREPARING → RUNNING → SUCCEEDED
                                ├──→ PARTIAL_FAILED
                                ├──→ FAILED
                                └──→ CANCEL_REQUESTED → CANCELLED

QUEUED / PREPARING 也可接收取消；准备失败进入 FAILED。
连接状态 UNKNOWN / CONNECTING / ONLINE / UNREACHABLE 独立于任务状态。

任务调度按节点串行。插件安装、切换环境和卸载对该插件加互斥锁；存在运行或排队引用时，先排空或由用户取消相应任务。输入清单与配置在提交后冻结。

批量任务至少一个成功且至少一个失败时为 PARTIAL_FAILED；全部失败为 FAILED；请求取消后保留已完成结果并标记完整性。完成与取消竞争时，执行端以首先提交的有效终态为准，取消接口返回“已完成”或“已请求取消”。

状态、事件和成功/失败计数由执行端统一提交。前端不根据进度百分比推导成功，也不因网络超时推导失败。应用重启后查询非终态任务；本机任务的正常退出提供等待或取消，远程任务可保留运行。

性能测试边界与可复现性

计时边界

字段定义
decode_ms节点本地读取与解码输入，不含网络上传；记录是否预加载。
preprocess_ms图像缩放、裁剪、颜色/布局和归一化转换。
inference_ms推理调用及必要的设备同步，具体是否包含设备拷贝在后端描述中注明。
postprocess_ms输出解析、分类排序、NMS、坐标还原等。
sample_total_ms从本地读取开始到得到统一预测结果；不含 UI 绘制、输出图片写盘和网络。
processing_wall_ms正式处理循环的墙钟时间；不含模型加载、预热和传输。
artifact_write_ms / transfer_ms结果产物落盘、上传及下载分开计时。
node_task_wall_ms / client_wall_ms节点任务从准备到终态；客户端从提交到所需结果取回，分别记录。

正式测量默认预热 10 次、执行 100 次、batch=1、并发=1。模型加载单独计时。采用节点上的单调高精度时钟；GPU 按后端需要在测量边界同步，不能用主机与客户端时钟相减计算推理时长。

平均值、P50、P95 基于正式成功样本的明确计时字段，报告统计数 N 与失败数；百分位采用线性插值并记录算法。吞吐量为 成功样本数 / processing_wall_seconds，失败处理消耗的时间仍在窗口中。取消或部分失败须保留相应标记。

提供两种明确模式：管线模式包含读取/解码；纯推理模式使用预先准备的张量，只支持具有分阶段能力的插件。不能将两种模式的数据混为同一性能结果。

报告快照

  • 模型/标签/输入清单摘要，插件与 SDK 版本，实际完整参数和配置修订。
  • 系统、CPU、GPU/驱动、后端/Provider、Python 与关键依赖版本、环境指纹。
  • 输入形状、批大小、线程、精度、预热与执行次数、输入缓存策略、计时能力和同步方式。
  • 内存采样周期及采样峰值；GPU 采样支持时标明范围，避免把采样峰值表述为精确瞬时峰值。

后续精度评估独立于性能模式。分类需要明确标签和 Top-K 口径；检测采用选定 COCO 评估实现与类别映射。无标注、类别不匹配、样本失败等条件必须显式处理，不静默产生看似完整的精度指标。

13

兼容性、凭据与运行边界

方面设计约束
插件信任Python 插件以节点用户权限执行任意代码；虚拟环境用于依赖隔离，非安全沙箱。首版导入可信插件。
系统权限本机和远端优先用户目录安装，不默认请求管理员/root 权限或修改驱动。
凭据系统凭据库/SSH agent 持有身份材料；普通日志与报告不记录私钥、口令或连接令牌。
文件边界解包防路径穿越；产物路径在任务根内；外部文件引用明确所属节点，自动清理不触及用户原始目录。
Tauri 能力前端只调用受限 Rust 命令，配置 CSP；本地静态应用不加载第三方可执行页面。
系统兼容首批 Windows 10/11 x64；远端拟以 Ubuntu 22.04/24.04 LTS x64 建立验收矩阵。具体支持以验证记录为准。
GPU 兼容检查选定 Provider、运行库和驱动组合，不能仅根据发现显卡判断可用。CPU 与 GPU 方案分别锁定。
资源与日志任务有超时和取消边界；日志限速及轮转，资源采样低频执行并记录配置。

相同锁文件能约束包版本，但不会保证任意平台、原生库和驱动组合都可运行。插件声明的支持平台必须有对应构建/安装与加载测试记录。

实施顺序、风险与待决事项

阶段技术交付退出条件
M0协议草案落地、SDK PoC、uv CPU 环境、参考插件、SSH/SFTP 库互通验证。两个插件能被统一 Worker 加载，清单与结果协议稳定到可测试版本。
M1Tauri 本机应用、数据库、插件生命周期、任务监督、可视化、报告与安装器。本机从导入到报告形成闭环，故障与离线复用测试通过。
M2SSH 控制器、后台任务、SFTP 缓存、幂等与事件恢复、远程取消和结果取回。在支持矩阵节点完成断线测试，数据与任务状态一致。
M3选定 GPU 方案、性能校准、打包和完整回归。通过产品验收矩阵，发布明确的兼容性记录。
风险 / 待决事项处理方式
Windows SSH 库及 agent 兼容M0 实测后锁定库、算法支持和打包依赖。
Python 原生包与 CUDA 组合以运行方案锁定，维护已验证矩阵，检测失败不自动替换其他后端。
监督进程的登出存活能力探测与真实断线测试；记录主机策略限制，选择合适的用户级运行方式。
YOLO 输出变体先固定一种导出约定，其他变体通过新的模型声明/适配扩展。
权重与样本来源确认可分发范围、摘要和参考结果，再纳入验收资产。
缓存与空间增长首版提供空间统计和显式清理；自动配额/保留策略待实测后制定。
未定性能目标建立硬件基线后再给出吞吐和资源预算，当前只规定测量口径。
